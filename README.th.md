# คู่มือการทดสอบซ้ำ (ภาษาไทย)

คู่มือนี้สำหรับผู้ที่ต้องการทำการทดลองในบทความ *การพัฒนาและประเมินกลไกป้องกันการขายเกินในระบบจองห้องพัก* ซ้ำด้วยตนเอง หรือนำชุดคำสั่งไปทดสอบกลยุทธ์ของตนเอง ไม่จำเป็นต้องมีซอร์สโค้ดของ ARUN PMS ทุกอย่างที่ต้องใช้อยู่ในคลังนี้

ฉบับภาษาอังกฤษแบบย่ออยู่ที่ [README.md](README.md)

## 1. สิ่งที่ต้องเตรียม

| รายการ | รุ่นที่ใช้ในบทความ | หมายเหตุ |
|---|---|---|
| PostgreSQL | 16.13 | รุ่น 14 ขึ้นไปใช้ได้ ต้องมีส่วนขยาย `btree_gist` (มากับ PostgreSQL มาตรฐาน) |
| Node.js | 22.22.2 | รุ่น 20 ขึ้นไปใช้ได้ |
| Python | 3.12 | ใช้เฉพาะขั้นวิเคราะห์ผล |
| เครื่อง | 2 vCPU, RAM 7 GB, Ubuntu 24.04 | ค่าเวลาตอบสนองขึ้นกับเครื่อง แต่การขายเกินและยอดขายที่เสียไปไม่ขึ้นกับเครื่อง |

ใช้ **ฐานข้อมูลเปล่าสำหรับทดลองเท่านั้น** สคริปต์จะสร้างตาราง `rooms`, `res_x`, `res_n`, `idem` และล้างข้อมูลในตารางเหล่านี้ก่อนทุกรอบ ห้ามชี้ไปที่ฐานข้อมูลที่มีข้อมูลจริง

## 2. ติดตั้ง

```bash
git clone https://github.com/entgroupchannel-ctrl/arun-oversell-benchmark.git
cd arun-oversell-benchmark
git checkout v1.0          # รุ่นที่ใช้ในบทความ

npm install                # ติดตั้ง pg
pip install -r requirements.txt   # pandas, scipy, matplotlib
```

เตรียม PostgreSQL ชั่วคราวด้วย Docker (ง่ายที่สุด):

```bash
docker run -d --name pgbench -e POSTGRES_HOST_AUTH_METHOD=trust -p 5432:5432 postgres:16
```

หรือใช้ PostgreSQL ที่ติดตั้งอยู่แล้ว โดยสร้างฐานข้อมูลว่างหนึ่งฐาน เช่น `createdb oversell_bench`

## 3. ตั้งค่าการเชื่อมต่อ

สคริปต์อ่านค่าจากตัวแปรสภาพแวดล้อม

```bash
export PGHOST=127.0.0.1
export PGPORT=5432
export PGUSER=postgres
export PGPASSWORD=            # เว้นว่างถ้าใช้ trust
export PGDATABASE=postgres    # หรือ oversell_bench
export STMT_TIMEOUT=10000     # มิลลิวินาที บทความใช้ 10 วินาที
```

ตัวแปรอื่นที่ใช้ได้

| ตัวแปร | ค่าเริ่มต้น | ความหมาย |
|---|---|---|
| `POOL_MAX` | 100 | ขนาดกลุ่มการเชื่อมต่อ จำลองฟังก์ชันไร้เซิร์ฟเวอร์ที่ทำงานพร้อมกัน |
| `ONLY` | ทุกกลยุทธ์ที่ไม่ใช่ v2 | จำกัดกลยุทธ์ที่รัน คั่นด้วยจุลภาค |
| `OUT` | `results_<exp>.jsonl` | ไฟล์ผลลัพธ์ |

## 4. ทดลองรอบสั้นก่อน (ประมาณ 2 นาที)

ก่อนรันเต็ม ควรลองรอบเดียวเพื่อยืนยันว่าสภาพแวดล้อมถูกต้อง

```bash
OUT=smoke.jsonl node bench.mjs A 1
```

ควรเห็นบรรทัด `done A` และไฟล์ `smoke.jsonl` มี 72 บรรทัด (6 กลยุทธ์ × 4 ค่า N × 3 ค่า R) ตรวจคร่าวๆ ด้วย

```bash
grep -c . smoke.jsonl                                  # 72
grep '"strategy":"S0_naive"' smoke.jsonl | grep -o '"oversell_pairs":[0-9]*' | head -3   # ควรมากกว่า 0
grep '"strategy":"S5_hybrid"' smoke.jsonl | grep -o '"lost_sales":[0-9]*' | sort -u       # ควรเป็น 0 ทั้งหมด
```

ถ้า S0 ไม่ขายเกินเลยในรอบสั้น ไม่ผิดปกติ เพราะเป็นเหตุการณ์เชิงสุ่ม รันเต็ม 10 รอบจะเห็นชัด

## 5. รันการทดลองเต็มตามบทความ

| การทดลอง | คำสั่ง | จำนวนรอบ | เวลาโดยประมาณ |
|---|---|---|---|
| ที่ 1 เปรียบเทียบกลยุทธ์ S0–S5 | `OUT=data/final_A.jsonl node bench.mjs A 10` | 720 | 25–40 นาที |
| ที่ 2 ส่งคำขอซ้ำ | `OUT=data/final_B.jsonl node bench.mjs B 30` | 360 | 10–15 นาที |
| ที่ 3 หลังปรับปรุง S1′, S2′ | `ONLY=S1v2_direct_fixed,S2v2_ota_fixed OUT=data/final_C.jsonl node bench.mjs A 10` | 240 | 10–15 นาที |

เวลาส่วนใหญ่หมดไปกับเงื่อนไข N = 1,000 และกรณีที่คำขอรอจน `statement_timeout` (10 วินาที) โดยเฉพาะ S1 และ S2

ถ้าไม่ต้องการทับข้อมูลดิบของบทความ ให้เปลี่ยน `OUT` เป็นชื่ออื่น เช่น `OUT=my_A.jsonl` แล้วแก้ path ใน `analyze.py` หรือคัดลอกไฟล์ไปไว้ที่ `data/` ภายหลัง

## 6. วิเคราะห์ผลและวาดรูป

```bash
mkdir -p figures
python3 analyze.py
```

ผลลัพธ์

- `data/stats.json` ค่าสถิติทั้งหมดที่รายงานในบทความ (Kruskal–Wallis, Mann–Whitney U, Fisher's exact test, ก่อน–หลังปรับปรุง)
- `figures/fig_lost_sales.png` ยอดขายที่เสียไปตาม N และ R (รูปที่ 3 ในบทความ)
- `figures/fig_p95.png` เวลาตอบสนอง P95
- สรุปตารางที่ 2 พิมพ์ออกทางหน้าจอ

## 7. เทียบผลกับบทความ

ตัวเลขที่ควรได้ใกล้เคียง (ค่าที่ไม่ขึ้นกับเครื่อง)

| ตัวชี้วัด | ค่าในบทความ | ดูได้จาก |
|---|---|---|
| S0 ขายเกิน | 119 จาก 120 รอบ | `stats.json` → `t2[0].oversell_runs` |
| S4 ขายเกิน | 27 จาก 120 รอบ | `t2[4].oversell_runs` |
| S1, S2, S3, S5 ขายเกิน | 0 | `t2[1..3,5].oversell_runs` |
| ยอดขายที่เสียไป S1 / S2 / S3 / S5 | 36.3 / 11.0 / 15.7 / 0.0 % | `t2[*].lost_mean` |
| หลังปรับปรุง จองตรง / OTA | 0.2 / 0.0 % | `round2.direct.after.lost_mean`, `round2.ota.after.lost_mean` |
| การจองซ้ำเมื่อเปิดกลไก G5 | 0 ทุกรอบ | `tB` แถว `direct_arun`, `ota_arun` → `dup_mean` |

จำนวนรอบที่ขายเกินของ S0 และ S4 และร้อยละยอดขายที่เสียไปอาจต่างจากบทความได้เล็กน้อย เพราะเป็นผลของจังหวะเวลาที่คำขอมาถึง แต่**ลำดับและข้อสรุปต้องเหมือนเดิม** คือ S0 ขายเกินเกือบทุกรอบ S4 ขายเกินบางรอบ S1 เสียยอดขายมากที่สุด และ S5 ไม่ขายเกินและไม่เสียยอดขาย ค่าเวลา P95 ขึ้นกับเครื่องและไม่ควรนำไปเทียบตรงๆ

## 8. นิยามตัวชี้วัด (ตรงกับบทความ)

- **ยอดขายที่เสียไป (%)** = (min(N, R) − จำนวนห้องที่ถูกใช้จริง) ÷ min(N, R) × 100
- **การจองเกิน** = จำนวนคู่การจองที่อยู่ห้องเดียวกันและมีช่วงเข้าพัก `[check_in, check_out)` ทับกัน
- **ความผิดพลาด** = จำนวนคำขอที่สิ้นสุดด้วยข้อผิดพลาดหลังการลองใหม่ภายในของกลยุทธ์ (`40P01` ภาวะติดตาย, `57014` หมดเวลา)
- **P95** = เปอร์เซ็นไทล์ที่ 95 ของเวลาต่อคำขอ วัดตั้งแต่ขอการเชื่อมต่อจากกลุ่มจนคืน รวมเวลารอคิว การลองใหม่ และคำขอที่ล้มเหลว
- **การจองซ้ำ** (การทดลองที่ 2) = Σ(จำนวนแถวต่อรหัสการจอง − 1) และ **ตกหล่น** = จำนวนรหัสที่ไม่มีแถว
- **D** = จำนวนครั้งที่ส่งคำขอเดียวกันทั้งหมด รวมครั้งแรก

## 9. ทดสอบกลยุทธ์ของคุณเอง

กลยุทธ์คือฟังก์ชัน `async (client, source) => "booked" | "full"` ใน `bench.mjs` (วัตถุ `STRATEGIES` และ `FIXED`) ที่รับ connection จาก `pg` แล้วพยายามจองห้องประเภทเดียวกันในวันเดียวกันหนึ่งรายการ โยน error ออกมาได้ สคริปต์จะนับเป็นความผิดพลาด

ขั้นตอน

1. เพิ่มฟังก์ชันใหม่ใน `STRATEGIES` เช่น `S6_mine`
2. เลือกตารางให้ถูก: `res_x` มีข้อจำกัดแบบกีดกัน (`res_x_no_overlap`) และดัชนีกันซ้ำ `res_n` ไม่มีข้อจำกัดใดๆ
3. ใช้ `FREE(table)` เพื่อสร้างคำสั่งค้นหาห้องว่างแบบเดียวกับกลยุทธ์อื่น จะได้เทียบกันได้
4. รัน `ONLY=S6_mine,S5_hybrid OUT=mine.jsonl node bench.mjs A 10`
5. เพิ่มชื่อกลยุทธ์ในรายการ `order` ของ `analyze.py` ถ้าต้องการให้อยู่ในตารางและรูป

## 11. ปัญหาที่พบบ่อย

| อาการ | สาเหตุ / วิธีแก้ |
|---|---|
| `extension "btree_gist" is not available` | ติดตั้งแพ็กเกจ contrib ของ PostgreSQL (Ubuntu: `postgresql-contrib`) หรือใช้ภาพ Docker `postgres:16` |
| `ECONNREFUSED` | ตรวจ `PGHOST`/`PGPORT` และว่า PostgreSQL รันอยู่ |
| `too many clients already` | ลด `POOL_MAX` หรือเพิ่ม `max_connections` ของ PostgreSQL ให้มากกว่า 100 |
| รันช้ามากที่ S1, S2 | ปกติ เพราะคำขอที่ชนกันรอจนครบ `STMT_TIMEOUT` ถ้าต้องการเร็วขึ้นในการทดลองส่วนตัว ลดเป็น `STMT_TIMEOUT=3000` แต่ค่า timeout จะเพิ่มขึ้น |
| ผล S0 ไม่ขายเกินเลย | เพิ่มจำนวนรอบ หรือเครื่องมีแกนประมวลผลน้อยจนคำขอไม่ได้ทำงานพร้อมกันจริง ลองเพิ่ม `POOL_MAX` |
| `analyze.py` หา `data/final_C.jsonl` ไม่พบ | ต้องรันการทดลองที่ 3 ก่อน หรือใช้ไฟล์ของบทความที่มีอยู่ใน `data/` |
